# P3 Stage 4 — System Integration Audit (Issue #49) — Design

**Issue:** #49, "[P3] Implement Stage 4 — System Integration Audit"
**AC:** audit checks physical/economic/historical/narrative consistency across all Confirmed World Entries; flags redundancy for simplification and any unresolved Dependency Review items; produces a summary the author must explicitly approve before Stage 5 (Compile) can proceed.

## What exists vs. what's missing — investigated first

Project 1's Stage 7 Creative Audit (`canonEngine/stage7Audit.ts`) is the only existing precedent for "system computes a structured audit → persists it → gates the next stage on explicit author acknowledgment → re-injects the summary into grounding while stuck." It is **P1-specific in every concrete respect** (hardcoded element ids like `"climax"`/`"core_dramatic_question"`, a rules-based word-overlap heuristic comparing exactly two named elements, its own `Story.stage7Audit` field and its own gate wired directly into `chat/route.ts`'s stage-advance loop) — reusable as a *pattern*, not as code, the same conclusion reached for #45/#46/#47/#48's own "shared component" investigations.

Two deeper gaps, found by investigation rather than assumed:

1. **P3 has zero app-level stage enforcement today.** `current_stage` is a plain model self-report (`z.number().int().min(1).max(5)`), never persisted on the Story doc, never compared against a prior value, never gated by anything. The model could report `current_stage: 5` on turn one with nothing Confirmed and nothing would stop it. There is no P3 equivalent of P1's `stageFsm.ts` (which is itself explicitly documented as "Project-1-specific... since the stage list and required elements are Project 1's own workflow" — not something to extend, per that file's own header comment).
2. **"Unresolved Dependency Review items" has no persisted concept to query.** Both existing Dependency-Review mechanisms (issue #48's pillar confirm-gate, and the `cascadeReview` shown after resolving a Confirmed-entry conflict via Revise) are synchronous, inline, always-immediately-resolved interactions — neither is ever stored as an open/pending item. Reinterpreting the AC literally as "query a backlog of previously-shown-and-dismissed reviews" would require inventing new persisted state nothing in this codebase currently has a use for. The more consistent reading, matching Stage 7's own precedent of live recomputation (never a historical-flag lookup), is: **at audit time, recompute the dependency graph fresh and flag any structural problem found right then** — specifically, any Confirmed entry that depends on an entry which isn't itself Confirmed (an "unresolved" dependency, in the sense that its downstream implications haven't been settled). This is a live check, not a queue.

## Design decisions

**1. Three-part detection, matching what's actually rules-computable vs. not.** Investigated whether "physical/economic/historical/narrative consistency" could be rules-based like Stage 7's checks — it can't: Stage 7's heuristic only works because it compares exactly two *named, fixed* elements by shared vocabulary; World Entries have no such fixed pairing, and detecting a genuine contradiction across arbitrary free-text `functionalDescription`/`governingRules` content spanning however many Confirmed entries exist is not something a word-overlap heuristic can do at that scale. So:
   - **Dependency completeness** (rules-based, reuses issue #48's primitives): for every Confirmed entry, check every id in its `depends_on` — flag if that dependency isn't itself Confirmed. This is the audit's answer to "unresolved Dependency Review items," made concrete per the reasoning above.
   - **Redundancy** (rules-based, mirrors Stage 7's own technique applied to a different domain): pairwise shared-word overlap between Confirmed entries' `functionalDescription`, scoped to entries sharing the same `category` (bounding the comparison space — realistic per-story entry counts are in the tens, not thousands, so an O(n²) same-category comparison is cheap).
   - **Consistency** (model-driven, the one part with no rules-based precedent to lean on): a single one-shot Anthropic call, structurally extracted via the same generic `extractTurn` machinery every other P3 turn already uses, given all Confirmed entries' structured fields and asked to identify physical/economic/historical/narrative contradictions. This runs once per audit computation (not per chat turn), so it doesn't add per-turn latency/cost the way an unscoped grounding block would.

**2. A new, P3-local `P3Stage4Audit` type and store field — not a reuse of `Stage7AuditResult`.** Same reasoning already established for every other P3-vs-P1/P2 type this session (`P3PendingConflict` vs `StoryPendingConflict`/`P2PendingConflict`, `P3ConflictLogEntry` vs `CharacterConflictLogEntry`): each project's audit-shaped state is its own bespoke copy, not a generalization, since the finding categories and gating semantics genuinely differ (P1's checks are fixed-pair comparisons; P3's are graph-completeness + redundancy + model-driven consistency).

**3. Explicit approval, not Stage 7's "any reply counts" heuristic.** The AC says the author "must explicitly approve" — stronger than Stage 7's weaker "your next message, whatever it says, flips `authorResponded`." A new turn-schema field, `stage4_audit_approved: z.boolean()`, is set `true` by the model only on the turn where the author has just given a clear, unambiguous approval — mirroring how `resolution`/`validated_status` already require a clear verdict rather than treating any reply as consent.

**4. Narrow stage-clamping, not a general P3 stage-enforcement system.** Building full authoritative stage tracking for all 5 P3 stages is disproportionate to this issue and not what the AC asks for. Scope is narrow: the app only intervenes at the 4→5 boundary. On any turn where the model reports `current_stage >= 4` and no audit has been computed yet for this story, compute one now. On any turn where the model reports `current_stage: 5` while the persisted audit's `authorApproved` is still `false`, the app clamps the stage shown to the author back to `4` (overriding the model's self-report) and injects a grounding note telling the model an unapproved audit is blocking Compile. Stages 1-3 remain exactly as unenforced as they are today — untouched, out of scope.

**5. UI: a dedicated audit card, mirroring the established `ConflictCard` pattern, not a full recomputation of Stage 7's chat-only presentation.** A visible summary of findings (grouped by the three categories) with a single "Approve and continue to Compile" button that sends a canned, unambiguous approval message through the normal chat flow — consistent with how issue #47's `ConflictCard` and issue #48's confirm-then-retry both chose a real UI affordance over relying on the model to correctly interpret conversational nuance.

## Error handling

The model-driven consistency call follows the same pattern as every other `extractTurn` call in this route: a `RateLimitTimeoutError`/`TurnValidationError` during audit computation degrades to a clear, author-facing message (not a raw 500) rather than silently skipping the consistency check — the audit should visibly say "the consistency pass couldn't complete, try again" rather than quietly omitting it, since a systems-integration audit that silently drops one of its three checks would be worse than one that fails loudly. The rules-based checks (dependency completeness, redundancy) never fail in a way that needs error handling — they're pure computation over already-fetched data.

## Out of scope

- Stage 5 (Compile) itself — a separate, not-yet-built issue; this issue only builds the gate that blocks reaching it.
- Enforcing stages 1-3 — untouched.
- Any change to how Dependency Review is shown inline (issue #48's mechanisms) — this issue only adds a second, independent, live-recomputed check of the same underlying graph at audit time.
