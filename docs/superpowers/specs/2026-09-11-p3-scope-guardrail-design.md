# P3 Scope-Boundary Guardrail (Issue #46) — Design

**Issue:** #46, "[P3] Implement scope-boundary guardrail layer"
**AC:** a real (not persona-instruction-only) check runs before an assistant response is shown, catching content that belongs to Character Bible (Project 2), Story Architecture (Project 4), or Draft Writing (Project 5) scope; redirected responses acknowledge, flag as out-of-scope, and offer to log the item for the correct project instead of executing the work.

## Reuse reality check — the claimed shared `GuardrailRunner` doesn't exist

The issue's architecture note says to "build as the shared `GuardrailRunner` middleware (declarative rule set + redirect pattern) rather than an independent implementation," citing #32 (P2, closed) and #68 (P4, not yet built) as peers. Investigated before designing, same as #45's reuse claim was investigated: **`GuardrailRunner` is a name that exists only in `ARCHITECTURE.md` prose — there is no such module anywhere in the codebase.** `ARCHITECTURE.md` §7 itself, written after the fact, concedes this: unlike every other shared-engine row (`CanonElement`, `StructuredDeltaExtractor`, `ConflictResolution`, side panel, `DocumentCompiler`), `GuardrailRunner` "has no Project 1 reference implementation... its three peer implementations are #32 (P2), #46 (P3), #68 (P4), cross-referenced to each other instead." Peers, not a chain of build-once-reuse-thrice. #68 isn't built, so #32 is the only real data point.

What #32 actually built, read in full: a required `deferred_items` field on `CharacterTurnSchema`/`EMIT_CHARACTER_TURN_TOOL` (the model self-reports out-of-scope content it noticed), mapped to `StoredOutstandingQuestion` and persisted via the already-generic `appendOutstandingQuestions()`/`listOutstandingQuestions()` (`web/src/lib/canonEngine/storyStore.ts`, originally Project 1's, already collection-agnostic across all four projects' `defer_to` values). That persistence layer is genuinely reusable — no changes needed. But the *detection* is pure model self-report: nothing re-checks `reply` against `deferred_items`, and there is no coded redirect-message template — the "acknowledge, flag, offer to log" pattern is prose shaped only by system-prompt instruction (sp02 §3), unverified by any code.

**This matters because #46's own AC text explicitly rules out exactly that:** "This check is implemented as real logic (not solely relying on persona instructions), since the PRD explicitly flags prompt-only enforcement as insufficient over long sessions." A literal port of #32 would inherit its exact gap — detection that's entirely persona-instruction-dependent, the specific failure mode the AC is written against. So #46 needs to do genuinely more than #32 did, not less than the issue asked for.

## Design: two detection layers, one deterministic enforcement point

**Layer 1 (primary, broad coverage) — model self-report, mirroring #32's proven mechanism.** Add `deferred_items: DeferredItemInput[]` (required, can be empty) to `WorldTurnSchema`/`EMIT_WORLD_TURN_TOOL`, same shape as P2's (`item`, `defer_to_project`, `notes`), with `defer_to_project: z.enum(["Project 2", "Project 4", "Project 5"])` (the three projects P3 can defer to — excludes Project 1 and Project 3 itself, mirroring how P2's enum excludes Project 1 and Project 2). This is genuinely reusable: same schema shape, same `appendOutstandingQuestions()` call, same `defer_to` union already covering all four downstream values. No new store logic.

**Layer 2 (secondary, narrow high-precision safety net) — a real rules-based check, specifically for Project 5 (prose/dialogue generation).** This is the layer that actually answers the AC's "not solely relying on persona instructions" requirement, and it's scoped deliberately narrow rather than attempting a general-purpose classifier for all three domains:

- **Why only Project 5, not also Project 2/Project 4 rules-based detection:** Character-psychology and plot-structure content overlap heavily with legitimate World Bible content — sp03 §4 itself says P3 should "focus strictly on how macro cultural/societal facts objectively impact the characters" (so *mentioning* characters is expected, not a violation) and the World Bible's own "History" pillar legitimately covers a world timeline (so *timeline* language isn't reliably a Project 4 tell either). A keyword/pattern rule for these two domains would have a high false-positive rate against core, legitimate World Bible content. Building a reliable classifier for them is disproportionate to this issue's scope and risks blocking good content more often than it catches bad content. For these two, Layer 1 (self-report) is the detection mechanism, same as #32 — an honest, documented limitation, not an oversight (see Open Follow-up below).
- **Why Project 5 is different:** prose/dialogue generation has a genuinely distinctive, high-precision signature — attributed quoted dialogue (`Name: "..."` or `"..." said Name`) or a block of past-tense narrative action prose — that essentially never appears in legitimate World Bible output (which describes rules, systems, and facts, not scenes). This is also the domain the AC's own cited concern (a model drifting into doing another project's work over a long session) most plausibly threatens, since actually writing prose is the clearest version of "executing the work" the AC says must not happen.
- **Detection function:** `detectProseGeneration(reply: string): boolean` in a new module, conservative by design (tuned toward under-triggering, not over-blocking) — requires a reasonably strong signal (e.g. two or more attributed dialogue lines, or a multi-sentence past-tense narrative block) rather than firing on a single quoted word. Like issue #20's classifier tuning, the exact threshold will likely need adjustment once there's real usage data; ship a clearly-isolated, easily-tunable function rather than scattering the heuristic inline.

**Enforcement (the actual "real logic" the AC calls for) — the app constructs the redirect text, not the model.** Whenever either layer flags a deferral, `world-chat/route.ts` builds the author-facing acknowledgment deterministically via a new `buildScopeRedirectNote(items)` function — a fixed template naming the correct on-screen project ("Character Bible", "Story Architecture", "Draft Writing" — matching this route's existing closing-reminder convention of only ever naming author-facing product terms, never internal project numbers beyond "Project 2"/"Project 3" which that reminder already allows) — rather than trusting the model's own prose to phrase the pattern correctly every time.

- **Layer 1 deferrals (self-reported):** the model already recognized the topic and, per prompt instruction, is expected to have already steered the conversation appropriately in its own `reply`. The deterministic note is *appended* after `delta.reply` (not a full replace) — this reinforces the pattern with guaranteed wording without discarding whatever legitimate, in-scope content the same turn may also contain.
- **Layer 2 deferrals (rules-detected prose):** genuine off-scope content was actually generated. Per the AC ("offer to log it... instead of executing the work"), the drafted prose must never reach the author. `delta.reply` is *fully replaced* with the redirect note in this case — the one place this feature actively discards model output, and only for the highest-precision, highest-stakes signal.
- Both cases persist via `appendOutstandingQuestions(storyId, [...])`, `defer_to` set from `defer_to_project` (Layer 1) or hardcoded `"Project 5"` (Layer 2, with a synthesized `item`/`notes` describing what was caught, e.g. "Drafted narrative prose was blocked from an in-World-Bible turn").

## What's genuinely reusable vs. new

- Reusable as-is: `appendOutstandingQuestions()`/`StoredOutstandingQuestion` (`storyStore.ts`), the `defer_to` union (already includes `"Project 3"` and the three deferral targets), `extractTurn()`'s existing generic retry-on-validation-failure behavior (no new code needed there — same as #43's Task 3 finding for its own schema additions).
- New: the `deferred_items` schema field on `WorldTurnSchema`/`EMIT_WORLD_TURN_TOOL` (mechanical port of #32's shape — note `characterTurnSchema.ts` does export `DeferredItemSchema`/`DeferredItemInput`, but its `defer_to_project` enum is P2's own three values; rather than cross-import `characterEngine` from `worldEngine` (no existing precedent for that direction) or generalize the enum for one field, define a P3-local equivalent with P3's own enum values, matching how each project's turn schema is otherwise self-contained today); `detectProseGeneration()` (new, P3-specific, in a new `web/src/lib/worldEngine/scopeGuardrail.ts`); `buildScopeRedirectNote()` (new, same file); the wiring in `world-chat/route.ts` that runs Layer 2 detection, decides append-vs-replace, and persists.
- **Not touched:** `turnGuardrails.ts` — confirmed to be an unrelated mechanism (prompt/schema-leakage logging, issues #5/#27/#110), not scope-boundary detection. This issue adds a sibling module, not an extension of that one.

## Error handling

- A failed `appendOutstandingQuestions()` call degrades the same way #43 established for Stage 3's store calls: logged via `console.warn`, never a hard error to the author — the turn still completes and shows the redirect note even if the underlying log-for-later write fails.
- `detectProseGeneration()` is pure and synchronous (regex/pattern matching over already-generated text) — it cannot itself fail in a way that needs error handling; a false negative (missed prose) just means Layer 2 didn't catch it, not an exception.

## Open follow-up (documented, not fixed here)

- Layer 2's Project 5 rules-based check will need empirical tuning once there's real usage data (mirrors issue #20's already-acknowledged classifier-tuning gap) — ship it isolated in one function specifically so that's cheap to do later.
- Project 2/Project 4 detection relies entirely on the model's self-report (Layer 1), same limitation #32 has today. If drift is observed in practice (the model executing Character Bible or Story Architecture work without self-flagging it), a future issue could add a secondary small-LLM classification call for those two domains specifically — the AC raises this as an option; this design doesn't build it now because there's no evidence yet that Layer 1 alone is insufficient for these two less-precisely-detectable domains, and building an unvalidated classifier now risks solving a problem that may not occur while adding false-positive risk that definitely would.
