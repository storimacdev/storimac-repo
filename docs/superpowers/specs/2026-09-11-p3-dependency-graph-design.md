# P3 Systemic Dependency Graph & Dependency Review Trigger (Issue #48) — Design

**Issue:** #48, "[P3] Implement Systemic Dependency Graph & Dependency Review trigger"
**AC:** world pillars and assets are linked in a dependency graph (e.g. Geography → Economy → Politics → Culture, plus cross-references between individual entries); changing a `Confirmed` element automatically triggers a Dependency Review prompt listing everything downstream that references it, before the change is finalized; the author must acknowledge/resolve the review before the change commits.

## What already exists vs. what's missing — investigated first

This is the issue three prior reviews (#42, #46, #47) explicitly deferred a fix to: `canonStore.ts`'s `listDependents`/`listDownstreamImpact` are hardcoded to the `"elements"` collection (Project 1's own), so nothing built for P3 could reuse them — issue #47 built a local, P3-scoped `computeCascadeReview` workaround specifically to avoid stepping on this issue's territory. That fix is genuinely small: both functions gain a `collection: string = "elements"` parameter (fully backward-compatible; exactly one non-default caller needed anywhere in the repo). Once fixed, #47's `computeCascadeReview` is rewired onto the real function — same Confirmed-filter, same result shape, provably identical output for the entry-level case, just no longer a parallel implementation.

That fix alone does **not** deliver this issue's AC, though. Investigation found two deeper gaps:

1. **Chat-authored World Entries have no way to declare cross-references.** `WorldTurnSchema.proposed_entry` has exactly 8 fields (name, category, narrative_role, importance, depth, functional_description, governing_rules, entry_id) — no `depends_on`. Only the direct CRUD API lets a human set it by hand. So even with the shared function fixed, the Dependency Review will almost always come back empty for the vast majority of entries (everything authored through chat, not the direct API).
2. **Pillars have zero Confirmed-change protection, and zero way to declare pillar-to-pillar dependencies at all.** `canon-status/route.ts` (the pillar status PATCH) calls `upsertElement` with `allowConfirmedOverride` **hardcoded to `true` unconditionally** — no detection, no review, no blocking step. Its own comment reasons this is fine because "every call here is... an explicit author button-click," which is true, but the AC's own headline example (Geography → Economy → Politics → Culture) is specifically a *pillar*-level chain, and today there is no data-entry point for the model or author to ever record "Economy depends on Geography" — pillar `CanonElement`s have `value: null` and `depends_on: []` forever. sp03 §5 already instructs the model to "treat the world as a causal chain" and review dependents when a pillar changes — but nothing downstream of that prompt instruction (schema, store, guard, UI) implements it. It's unrealized intent today, not a partially-built feature.

## Design decisions

**1. Fix the shared functions, rewire #47's workaround onto them.** Mechanical, two files (`canonStore.ts`, `stageFsm.ts`), no behavior change for Project 1's existing callers (default parameter). `computeCascadeReview` keeps its own Confirmed-filter and `{entryId, name}` mapping — the shared function returns raw `CanonElement[]`, unfiltered by status, same as it always did for P1.

**2. Give chat-authored World Entries a `depends_on` field.** Add `depends_on: z.array(z.string())` (required, can be empty — same pattern as `deferred_items`) to `WorldTurnSchema.proposed_entry`, wired into `entryInput` in `world-chat/route.ts`'s Stage 3 block. This is the direct fix for AC-1's "cross-references between individual entries" — no new store logic needed (`createWorldEntry`/`updateWorldEntry` already accept `dependsOn` in their input types; the chat handler just never passed it through).

**3. Pillar Confirmed-change protection is a synchronous confirm-then-retry gate, NOT a replica of issue #47's chat-turn Conflict Resolution flow.** This is the load-bearing design call in this spec, so the reasoning: issue #47's Revert/Revise/Defer protocol exists because entries are edited *by the model*, mid-conversation, where "halt and ask the model to relay 3 choices to the author" is the only way to intervene. Pillars are different — `canon-status/route.ts`'s own existing comment already correctly identifies every pillar-status change as "an explicit author button-click," never a model proposal. There is no model turn to inject a grounding block into, and the Revert/Revise/Defer vocabulary doesn't even map cleanly onto a pillar (there's no "proposed new value" to revise — only a status transition). Building a parallel turn-based protocol for a synchronous button click would be needless complexity solving a problem that doesn't exist for this case.

Instead: `canon-status/route.ts`'s PATCH gains a two-step confirm flow, the standard pattern for "this is a bit destructive, are you sure" UX:
- On a request to move a `Confirmed` pillar to any other status, compute the Dependency Review (dependents via the now-fixed `listDependents(storyId, elementId, WORLD_ELEMENTS_COLLECTION)`, filtered to Confirmed, same shape as the entry-level review).
- If dependents exist and the request body doesn't include `acknowledged: true`, respond `409` with `{ needsAcknowledgment: true, dependencyReview: [...] }` — nothing is written yet.
- The author's UI shows the review; if they confirm, the UI re-sends the identical PATCH with `acknowledged: true`, which then proceeds to the actual `upsertElement` write exactly as today.
- If dependents don't exist, the change commits immediately with no extra round-trip (no dependency, nothing to review) — matches the AC's own conditional framing ("listing everything downstream that references it").

**4. Pillar-to-pillar dependencies are model-declared, mirroring how `proposed_pillars` itself already works.** Add `pillar_dependencies: z.array(z.object({ pillar: z.string(), depends_on: z.array(z.string()) }))` to `WorldTurnSchema` (top-level, like `proposed_pillars`, not nested in `proposed_entry` — pillar relationships aren't tied to a single entry proposal). Wired into `world-chat/route.ts`: for each `{pillar, depends_on}` pair, `upsertElement(storyId, pillarElementId(pillar), { depends_on }, ..., WORLD_ELEMENTS_COLLECTION)` (creating the pillar's `CanonElement` if it doesn't exist yet, exactly as pillars already get lazily created on first status-set per issue #41's design). This is what actually gives AC-1's pillar-chain example (Geography → Economy → Politics → Culture) real, persisted data to review — without it, step 3's whole confirm-gate would have nothing to ever show.

**5. Not doing (documented, not silently dropped): Project 1's rationale-text-scan half of a Dependency Review.** P1's own `findCascadeReview` unions the structural `depends_on` query with a substring scan of every Confirmed element's `rationale` field for a mention of the changed element's id — a looser, textual "might reference this" signal on top of the strict structural one. Fixing the collection parameter does not bring this in automatically; it is deliberately not added here, since World Entries don't have a `rationale` field in the same sense P1's elements do (their prose lives in `functionalDescription`/`governingRules`, free text a substring match on a raw entry id would rarely hit meaningfully), and it would be a second, independent design decision beyond this issue's core ask. Noted as an explicit non-goal, not a silent gap.

## Error handling

Every new write (`upsertElement` for pillar dependencies, the pillar confirm-gate's eventual commit) follows the existing degrade-gracefully convention: within `world-chat/route.ts`'s existing try/catch blocks for Stage 3-adjacent writes. The confirm-gate's `409` response is not an error in the app's own sense — it's an expected, structured "not yet, here's why" response the UI is built to handle, same shape as any other soft-block this codebase already uses (e.g. the Character Bible gate's `400` with a message).
